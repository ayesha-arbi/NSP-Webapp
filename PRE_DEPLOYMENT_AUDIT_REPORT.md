### Application Architecture: One App or Two?
The code inspection determined that the **Issuer Portal** and **Verifier DApp** are **two integrated sections of a single React single-page application (SPA)**, rather than two separately buildable applications.
* Both sections are declared and mounted inside `src/App.tsx`.
* Switching between the sections is governed by the state variable `activePortal` (`"issuer"` | `"verifier"`), controlled through the persistent top Portal Mode switcher bar (`renderPortalSwitcher()`).
* Both portals share a single build artifact output (`dist/`) generated by Vite.

### Routing Architecture & Mapped Screens
Navigation within the application is entirely state-driven via React `useState` hooks. Although `react-router-dom` (v7.18.4) is present in `package.json`, it is not imported or used anywhere in `src/`.

#### Verifier DApp Screens
1. **Landing Screen (`LandingScreen.tsx`)**: The public entry point. Provides access to QR scanning and manual entry, displays process guides, and details the three-step blockchain verification concept.
2. **QR Scanner Screen (`QRScannerScreen.tsx`)**: Simulates a camera scanning viewfinder with animation, permission handling states, format validation error displays, and camera privacy notices.
3. **Manual Entry Screen (`ManualEntryScreen.tsx`)**: Text input with strict format checking (prefix `NSP-`), live 5-step animated verification progress, and demo ID handlers (`NSP-004821` for Verified, `NSP-T001` for Tampered, `NSP-R001` for Revoked, and `NSP-X001` for Not Found).
4. **Verification Result Screen (`VerificationResultScreen.tsx`)**: Presents verified worker information, grade, issue date, testing centre, and cryptographic transaction hash. Includes utility buttons to copy the verification receipt, trigger browser printing, and download a text report.

#### Issuer Portal Screens
1. **Authentication (`LoginScreen.tsx` & `MFAScreen.tsx`)**: Email/password form validation, demo accounts selector, account lockout modal with countdown timer, unauthorized device modal, 6-digit OTP MFA verification, and backup code recovery modal.
2. **Dashboard (`DashboardScreen.tsx` & `SuperAdminDashboard.tsx`)**: Role-customized views displaying enrolled candidate stats, draft counters, hub progress meters, recent candidates table, and cross-hub administrative metrics.
3. **Candidate Enrollment (`EnrollmentScreen.tsx`)**: Multi-field candidate intake (Full Name, Father's Name, DoB, CNIC, Trade, Hub), simulated NADRA identity verification, and AWS S3 pre-signed photo upload workflow.
4. **Assessments (`AssessmentScreen.tsx`)**: 5-criterion rubric scoring, automatic grade computation, idempotent draft saving and submission via `clientRequestId`, and offline storage in IndexedDB (`idb-keyval`).
5. **Approvals Queue (`ApprovalsScreen.tsx`)**: Center Superintendent hub-scoped review queue, status and trade filters, approval signing modal requiring passphrase, and rejection feedback modal.
6. **Auxiliary Management Screens (`CredentialsScreen.tsx`, `CredentialRevocationScreen.tsx`, `DevicesScreen.tsx`, `SettingsScreen.tsx`, `NotificationsScreen.tsx`, `UserManagementScreen.tsx`)**: In-memory administrative mock interfaces for device health, user roles, system alerts, and security settings.
7. **Orphaned / Unlinked Screen (`CandidateRecordScreen.tsx`)**: Registered in `App.tsx` as `record-detail`, but currently unlinked from any dashboard or enrollment table row.

## 4. Findings and Fixes Register

### [F-01] TypeScript TS1005 Syntax Errors in Inline Types
* **Severity**: **High**
* **Application / Area**: Shared components, screens, and services.
* **Description & Evidence**: Running `npx tsc --noEmit` failed with 11 errors:
  * `src/components/Layout.tsx:33`: `TS1005: ';' expected` in Icon props.
  * `src/components/NavBar.tsx:2`: `TS1005: ';' expected` in breadcrumbs type.
  * `src/screens/NotificationsScreen.tsx:168`: `TS1005: ';' expected` in categoryColors.
  * `src/screens/SettingsScreen.tsx:365`: `TS1005: ';' expected` in tabs type.
  * `src/screens/SuperAdminDashboard.tsx:1518`: `TS1005: ';' expected` in TABS type.
  * `src/services/api.ts:343`, `line 470`: `TS1005: ';' expected` in return types.
  * `src/services/offlineQueue.ts:42`: `TS1005: ';' expected` in parameter type.
* **Root Cause**: Object type literal properties omitted delimiter characters (semicolons/commas), which Vite's esbuild transpiler leniently stripped during build, but standard TypeScript compiler (`tsc`) rejected as syntax errors.
* **Fix Applied**: Added semicolon property separators in all 8 declarations across the 6 affected files.
* **Approval Status**: Approved in Implementation Plan.
* **Retest & Result**: `npm run typecheck` exited code 0 with 0 errors. **PASS**.

---

### [F-02] Session State Desynchronization on Page Refresh
* **Severity**: **Medium**
* **Application / Area**: Issuer Portal (`src/App.tsx`).
* **Description & Evidence**: When an authenticated user refreshed the browser, `sessionStorage` maintained `accessToken` and user state, but `App.tsx` initialized `const [screen, setScreen] = useState<AppScreen>("login")`. This resulted in the application rendering `LoginScreen` while the top header simultaneously displayed `Logged in: tradetester@nsp.com`.
* **Root Cause**: Hardcoded initial state `"login"` regardless of existing authenticated session.
* **Fix Applied**: Changed initializer to `useState<AppScreen>(() => authStore.getState().isAuthenticated ? "dashboard" : "login")`.
* **Approval Status**: Approved in Implementation Plan.
* **Retest & Result**: Tested with active session; page refresh correctly renders `DashboardScreen`. **PASS**.

---

### [F-03] Vite Production Chunk Size Warning (> 500 kB)
* **Severity**: **Low**
* **Application / Area**: Build Configuration (`vite.config.ts`).
* **Description & Evidence**: Running `npm run build` emitted `(!) Some chunks are larger than 500 kB after minification: dist/assets/index-DN2yRBLH.js (624.35 kB)`.
* **Root Cause**: All 14 screen components, UI icons, and the complete `ethers` library were bundled into a single monolithic entry chunk.
* **Fix Applied**: Configured function-based `rollupOptions.output.manualChunks(id)` in `vite.config.ts` to isolate `node_modules/ethers` and `node_modules/react`/`react-dom` into separate chunks.
* **Approval Status**: Approved in Implementation Plan.
* **Retest & Result**: `npm run build` completed in 2.67s with 0 warnings. Largest chunk is `index.js` at 404.69 kB, with `vendor.js` at 218.84 kB. **PASS**.

### [F-06] Build-Time Security Vulnerability in `source-map-js` (GHSA-68fv-2mgg-jv7q)
* **Severity**: **Low (Harmless in Production)**
* **Application / Area**: Dependencies (`package-lock.json`).
* **Description & Evidence**: `npm audit` reports 1 High severity vulnerability in `source-map-js` 1.2.1 (event-loop DoS during indexed source map parsing).
* **Root Cause**: Transitive build-time dependency of `@tailwindcss/vite` -> `@tailwindcss/node` -> `source-map-js` and `vite` -> `postcss` -> `source-map-js`.
* **Fix Applied / Recommendation**: Evaluated dry-run of `npm audit fix`, which pulled in 53 cross-platform packages and native binaries. Lockfiles were preserved without unnecessary upgrades because:
  1. `source-map-js` is strictly a build-time compiler dependency.
  2. It is never bundled into or executed in client browser runtime.
  3. `vite.config.ts` explicitly enforces `sourcemap: false` for production.
* **Approval Status**: Documented and verified as benign; no code changes required.

## 7. Security and API Findings

1. **No Exposed Secrets**: Comprehensive regex and grep scans confirmed no private keys, JWT signing secrets, database credentials, or production tokens exist in the repository.
2. **API Configuration**: Uses `VITE_API_BASE_URL` with a fallback to `http://localhost:3000`. Bearer token injection is managed in a single service function (`setApiAuthToken`).
3. **CORS Requirement**: `vite.config.ts` does not proxy `/api`. Direct browser requests require the backend server to configure CORS headers for the frontend origin.
4. **Session Storage**: Access tokens are stored in `sessionStorage` (tab-scoped) rather than `localStorage`, mitigating persistent cross-session token exposure.
5. **Vulnerability Assessment**: `source-map-js` 1.2.1 vulnerability is build-time only and benign in production runtime (`sourcemap: false` is configured).
